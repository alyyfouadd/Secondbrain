## Session 2 — 5:40 PM: Specifying the rebuild

Aly asked how to set up the same vault again, properly, with the same information but organised better.

### What Got Done

- Wrote [[Vault Rebuild Plan]] in Resources: the diagnosis, the route, the target shape, the four conventions, the order of work, the success tests and the honest cost.
- **Counted the drift rather than describing it**, so the problem is measurable: the vector-logo status is stated in **6 notes**, POLEKA's category in **6**, deliverable 2's filename in **3**. One decision therefore needs six edits, five get made, and the sixth rots. Every drift item in [[Vault Brief]] §5 is that one cause.

### Decisions Made

- **Argued against a new repo, and recommended rebuilding in place.** The content rewrite is identical either way and is 90% of the work; a new repo additionally loses the git history that is the only complete record of how each decision was reached, and costs the entire iPad setup again — Working Copy clone, Obsidian folder sync, git identity, default branch. No upside found.
- **The structure was never the problem, so most of it does not change.** Numbered folders, index-per-folder, the hub line, the boot-config split, the marketing pointer skill and append-only daily notes all stay exactly as they are.
- **The fix is four conventions rather than a new tree:** one fact one owner, current state on top with history below the line, status in a register row and never in prose, and one git ref always.
- **A client-level `Decisions.md` is the missing piece.** Decisions currently live inline as blockquotes correcting the paragraph above them, which is how a governance note ends up arguing with itself. It is also clause 4 armour.
- **Flagged the timing honestly rather than selling the job:** the full rebuild costs a session that ships no client work, against a Foundation due 9 October with four deliverables carrying no content. **Step 0, merging the four refs, is urgent regardless.**
